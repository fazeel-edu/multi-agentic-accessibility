SystemC_V1 architecture: explainer for supervision

Status: final spine, 2026-11-21. Source of truth for builders: ARCHITECTURE-SPINE.md (same folder). This page explains the design in plain terms. It gives guidance on a research prototype; it certifies nothing.

1. What is being built

A pipeline that audits a web page for accessibility two ways and scores both against a known answer key.

  • System A: axe-core, a rule engine. No language model.
  • System C: six role agents (screen reader, keyboard, colour and visual, cognitive, plain language, WCAG structure) run in parallel, then a synthesis agent reads all six results.
  • Pages: synthetic pages, generated by an LLM and reviewed by hand, with planted defects, clean controls and decoys. The answer key is written with each page, before any system runs.
  • Not in V1: System B (single agent), real public pages, expert audits. The design leaves a slot for each.

2. The shape: a staged pipeline

Capture the page once. Run a system on the saved capture. Clean up the results the same way for every system. Score. Show to a reviewer. Each stage only reads what the previous stage saved to disk.

pages + answer key -> capture -> (A | C) -> post-process -> report -> scoring + review screen

Why this shape: the research claim is a controlled comparison. If every system emits the same result format and goes through the same clean-up and scoring code, a difference in the numbers cannot come from plumbing.

3. Design decisions that protect the research

DecisionWhat it protects
One Auditor interface. A, C and later B are adapters.Scoring code never special-cases a system.
One capture per page, saved once, never edited. axe results are computed at capture time.A and C judge identical evidence.
The orchestrator is ordinary code with a fixed role table. Seven separate agent sessions, no lead model deciding who runs.No routing variance; every role runs once per page.
Tool allowlist enforced by a hook that fails closed. Roles can only read the capture.The "least tools per role" claim is real, not just configured.
Agents report evidence; code sets confidence, severity and rank.A model cannot inflate its own confidence.
One element-matching function shared by post-processing and scoring.Findings and answer key compare like with like; recall is not an artefact of selector formats.
Dev pages tune prompts. Test pages are only scored. Checked by code.No tuning on the test set.
Config, prompts, examples are hashed; a freeze tag blocks changes before the final run.Reproducible final run.
One cost ledger with a hard cap.Budget cannot be overrun by parallel agents.
Results are plain files. Scoring makes no API calls.Anyone can recompute the numbers.

4. One limitation to discuss

The proposal promised a fixed temperature. The Claude Agent SDK does not let us set temperature or an output-token cap (checked against current documentation). We pin what the SDK can enforce instead: model, effort, adaptive thinking, loop cap and cost cap. Sampling defaults become a stated limit, and the three repeated runs per page measure the resulting variation. The proposal wording should be amended. Using the raw Messages API would restore temperature control but means writing our own tool loop; this stays open for when System B is added.

5. What the numbers will and will not show

  • Pages and answer key are made by the same person who writes the prompts, and planted defects are cleaner than real ones. V1 numbers show the pipeline works. They are optimistic and not dissertation results.
  • Agents work from the accessibility tree and a scripted keyboard trace. This is not real assistive technology and not testing with disabled users.
  • With no System B, V1 can compare A with C only. The single-agent half of the hypothesis waits for the next phase.
